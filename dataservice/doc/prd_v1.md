## 1. 引言

### 1.1 目的

本文档定义 **DataFusion Hub**（一站式大数据接口平台）的产品需求，旨在为开发团队、利益相关者提供清晰、可执行的需求规格。核心目标是解决企业大数据集成中的碎片化问题：用户无需编写代码即可快速构建、发布和管理高性能API接口，覆盖数据接入、处理、消费全流程。PRD将指导MVP（最小可行产品）开发，并作为后续迭代的基准。

### 1.2 范围

- **包含内容**：
    - 数据源接入（批处理/流式）、API可视化设计、数据处理与转换、实时监控、安全治理、开发者门户。
    - 支持TB/PB级数据处理，兼容主流大数据技术栈（如Trino、Kafka、Spark、S3）。
    - 覆盖B2B场景：企业内部数据服务化（如金融风控API、电商用户画像API）。
- **排除内容**：
    - 数据存储底层实现（依赖云服务如AWS S3或HDFS，不自研存储引擎）。
    - 定制化AI模型训练（仅提供数据预处理能力）。
    - 非技术用户的数据分析功能（聚焦API接口层，非BI工具）。

### 1.3 定义、首字母缩写词和缩略语

| 术语 | 定义 |
|------|------|
| API | 应用程序编程接口，用于数据服务暴露 |
| ETL | Extract-Transform-Load，数据抽取、转换、加载 |
| SLA | 服务级别协议，定义性能与可用性标准 |
| RBAC | 基于角色的访问控制 |
| OAuth 2.0 | 开放授权协议，用于API安全认证 |
| DataFusion Hub | 本产品名称，一站式大数据接口平台 |
| MVP | 最小可行产品，V1.0核心功能集 |
| Trino | 分布式SQL查询引擎，用于统一查询多源数据 |
| GraphQL | API查询语言，提供灵活的数据获取方式 |
| Quarkus | Kubernetes原生Java框架，用于构建云原生应用 |

## 2. 产品概述

### 2.1 产品愿景与目标

- **愿景**：成为企业大数据服务的"统一网关"，让数据接口开发效率提升50%，降低90%的集成成本。
- **核心目标**：
    - **简化流程**：将数据从源到API的周期从周级缩短至小时级。
    - **统一平台**：整合数据接入、转换、发布、监控，替代分散的脚本和工具链。
    - **赋能开发者**：提供低代码/无代码体验，非专业数据工程师也能创建API。
    - **业务导向**：用户只需关注业务需求，无需了解技术细节。

### 2.2 目标用户与角色

| 角色 | 画像 | 核心痛点 | 使用场景 |
|------|------|----------|----------|
| **数据工程师** | 技术专家，负责数据管道构建 | 手动编写ETL脚本耗时，多源数据整合复杂 | 配置Trino流接入，设计数据转换逻辑 |
| **后端开发者** | API消费者，开发业务应用 | 依赖数据团队，等待接口就绪慢 | 调用平台生成的REST API获取用户行为数据 |
| **平台管理员** | IT运维/安全负责人 | 缺乏统一监控，安全策略碎片化 | 设置API限流规则，审计访问日志 |
| **业务分析师** | 非技术用户，需数据支持 | 无法直接获取数据，需提工单 | 通过开发者门户查看API文档和测试数据 |
| **业务部门负责人** | 业务决策者 | 不了解技术细节，难以评估API价值 | 审批API变更，评估业务影响 |

### 2.3 业务目标与成功指标

| 目标 | 衡量指标 | 目标值（MVP） | 目标值（V2.0） |
|------|----------|---------------|----------------|
| 提升开发效率 | API创建平均时间 | ≤2小时 | ≤30分钟 |
| 确保平台可靠性 | 系统可用性（SLA） | 99.9% uptime | 99.95% uptime |
| 降低运维成本 | 人均管理API数量 | ≥100个/工程师 | ≥500个/工程师 |
| 用户满意度 | NPS（净推荐值） | ≥40 | ≥60 |
| 资源优化 | "僵尸API"识别率 | ≥80% | 100% |

### 2.4 假设与依赖

- **假设**：
    - 企业已具备基础大数据基础设施（如Trino集群或云数据仓库）。
    - 用户接受基于云的SaaS部署模式（支持私有化部署选项）。
    - 业务用户不需要了解GraphQL/Trino等技术细节。
- **依赖**：
    - 第三方服务：Trino集群、云服务（AWS/Azure）。
    - 内部资源：后端团队需在3个月内完成核心引擎开发。

## 3. 用户需求

### 3.1 用户角色与画像

- **数据工程师（主要用户）**：
    - 需求：快速连接异构数据源，可视化定义转换逻辑，无需编码。
    - 痛点：现有工具（如Airflow）需编码，学习曲线陡峭。
- **后端开发者（关键用户）**：
    - 需求：即时获取API文档、测试端点，监控调用性能。
    - 痛点：API文档过时，调试困难。
- **业务分析师（扩展用户）**：
    - 需求：无需技术知识即可定义业务API。
    - 痛点：依赖数据团队，无法自主获取数据。

### 3.2 核心用户故事

| 用户角色 | 用户故事 | 优先级（MoSCoW） |
|----------|----------|------------------|
| 数据工程师 | 作为数据工程师，我希望能从Trino中抽取数据并自动转换为业务API，以便快速发布。 | Must have |
| 后端开发者 | 作为开发者，我希望能通过开发者门户实时测试API并查看响应示例，以便集成到我的应用中。 | Must have |
| 平台管理员 | 作为管理员，我希望能设置API调用的QPS限流和IP白名单，以防止滥用。 | Should have |
| 业务分析师 | 作为分析师，我希望能定义用户价值分析API（联合查询），无需编写SQL。 | Must have |
| 数据工程师 | 作为数据工程师，我希望能安全地下线废弃API，确保无业务影响。 | Must have |

## 4. 功能需求

### 4.1 数据接入管理

#### 4.1.1 多源连接器（优先级调整）

| 数据源类型 | 支持阶段 | 优先级 | 详细要求 |
|------------|----------|--------|----------|
| **Trino** | V1.0 | Must | - 必须支持Trino 400+版本<br>- 通过JDBC连接（默认端口8080）<br>- 自动发现Catalog/Schemata/Table结构<br>- 业务表别名映射（隐藏技术路径） |
| RocksDB | V1.5 | Should | - 仅支持本地文件模式（非集群）<br>- 需提供SST文件路径配置 |
| 关系型数据库 | V2.0 | Could | - MySQL/PostgreSQL via JDBC |
| Kafka/流数据 | V2.0 | Could | - 仅限V2.0后支持 |

#### 4.1.2 Trino连接器详细规范

| 功能模块 | 详细需求 | 验收标准 |
|----------|----------|----------|
| **连接配置** | - 提供向导式表单：<br>  • 必填：JDBC URL（自动补全`jdbc:trino://`前缀）<br>  • 可选：认证方式（无认证/Basic Auth/Kerberos）<br>  • 自动检测Trino集群健康状态 | - 输入无效URL时实时报错<br>- 支持保存连接模板 |
| **Schema发现** | - 自动加载Catalog列表 → 选择Schema → 展示表结构<br>- 支持业务表别名（如"用户基本信息表"而非`hive.user.profile`） | - Catalog加载时间≤3秒<br>- 业务表别名准确率100% |
| **数据预览** | - 点击表名后：<br>  • 默认预览前100条（可调采样率：1%~100%）<br>  • 支持简单过滤（如`WHERE date > '2025-01-01'`）<br>  • 类型推断（自动识别VARCHAR/TIMESTAMP等） | - 预览100万行表时，响应时间≤5秒<br>- 错误数据高亮显示 |
| **元数据同步** | - 定时同步Trino元数据（默认每24小时）<br>- 手动触发同步按钮 | - 元数据同步失败时触发告警<br>- 同步日志可追溯 |

#### 4.2.2 API配置模块

|----------|----------|----------|
| **基础配置** | • 路径规则：<br>  - 自动：`/api/v{version}/{business-domain}/{api-name}`<br>  - 自定义：支持正则 | • 路径必须以`/api`开头<br>• 版本号格式：v1/v1.0 |

| **流量配置** | • 限流策略：<br>  - QPS：全局/用户级<br>  - 突发流量：Burst=2×QPS<br>• 熔断机制：<br>  - 错误率>5% → 自动降级 | • QPS≥1000需管理员审批<br>• 熔断恢复时间≥30秒 |
| **数据转换** | • 字段级规则：<br>  - 脱敏（maskPhone/maskID）<br>  - 类型转换<br>  - 条件过滤<br>• 沙箱环境：<br>  - JavaScript执行（500ms超时） | • 沙箱禁止访问外部网络<br>• 敏感字段必须配置脱敏 |
| **错误处理** | • 自定义错误码：<br>  - 400：参数校验失败<br>  - 429：流量超限<br>  - 503：后端服务不可用<br>• 错误响应模板 | • 隐藏系统细节<br>• 业务错误码与HTTP状态分离 |

| **监控仪表盘** | • 实时指标：<br>  - QPS/延迟/错误率<br>  - 流量分布<br>  - 资源消耗<br>• 自定义视图 | • 数据延迟≤30秒<br>• 支持下钻分析 |
| **告警管理** | • 智能阈值：<br>  - 动态基线<br>  - 多条件组合<br>• 告警路由：<br>  - 按严重度分级<br>  - 多通道通知 | • P0告警必须5分钟内响应<br>• 告警风暴抑制 |
| **调用日志** | • 全链路追踪：<br>  - 请求ID贯穿所有服务<br>  - 记录完整请求/响应<br>• 敏感数据脱敏 | • 日志保留≥180天<br>• 敏感字段自动脱敏 |
| **生命周期管理** | • 状态机：<br>  - 设计 → 测试 → 生产 → 弃用 → 下线<br>• 自动化策略：<br>  - 90天未调用 → 标记为"废弃"<br>  - 180天未调用 → 自动下线 | • 生产环境变更需审批<br>• 下线前30天通知调用方 |

#### 4.2.4 API治理矩阵

| 治理维度 | 设计阶段 | 测试阶段 | 生产阶段 | 废弃阶段 | 验证方式 |
|----------|----------|----------|----------|----------|----------|
