# Quarkus+GraphQL+Trino Code Generation System - Architecture Design Document

## 1. System Overview

### 1.1 Core Concept Revision
Based on your clarification, the system design has been adjusted with the following understanding of "tenant":

- **Tenants are independent deployment units**, not customers sharing a single service instance
- Each tenant receives **a fully independent application instance** deployed in their own dedicated Kubernetes environment
- Data isolation is handled at the Trino layer through Ranger permissions management - **the application layer does not implement data isolation logic**
- Tenant configuration focuses on **deployment target information** (K8s namespace, domain, secrets) and **access control lists**

## 2. Redesigned System Architecture

### 2.1 Core Component Interaction
```
User Process per Tenant:
┌─────────────────┐    Clone & Configure    ┌─────────────────┐
│ Sample Repo     │ ──────────────────────> │ Tenant A Project│
│ Template        │                         │                 │
└─────────────────┘                         └─────────────────┘
                                              Execute Build
                                                    ↓
                                          ┌─────────────────┐
                                          │ Maven Build     │
                                          │ 1. Extract      │
                                          │    Framework    │
                                          │ 2. Generate     │
                                          │    Business Code│
                                          │ 3. Compile &    │
                                          │    Package      │
                                          └─────────────────┘
                                                    ↓
                                          ┌─────────────────┐

                                          │ Tenant A's      │
                                          │ Dedicated K8s   │
                                          │ Environment     │
                                          └─────────────────┘
```

### 2.2 Component Responsibilities
- **Sample Repository**: Serves as the starting template for single-tenant projects. Users clone a copy for each new tenant.
- **Framework JAR**: Provides the base Quarkus framework code, including simplified JWT validation (only username extraction and comparison).
- **Generator JAR**: Based on Handlebars templates, reads the **current tenant's** configuration files to generate business code and tenant-specific application configuration files.

## 3. Configuration System Design

### 3.1 Configuration Architecture
Each tenant project contains an independent configuration set, primarily divided into two categories:

1. **Tenant Deployment Configuration** (`tenant.yaml`): Defines the deployment target (K8s cluster, namespace, domain), resource specifications, allowed user list, and Trino connection information for that tenant's service.
2. **Table Field Exposure Configuration** (`tables/*.yaml`): Defines which Trino tables and fields to expose as GraphQL interfaces for that tenant.

### 3.2 Configuration File Description
- **`tenant.yaml`**: The core of tenant-specific configuration containing three sections: security (allowed user list), deployment (K8s target, domain), and data source (Trino connection).
- **`tables/*.yaml`**: Each file describes a table's exposure rules including field mapping and GraphQL operation types.

## 4. Code Generation Process

### 4.1 Single-Tenant Generation Workflow
1. **Preparation**: User clones the sample repository for Tenant A and edits its unique `tenant.yaml` and `tables/*.yaml` files.
2. **Execution**: User runs `mvn generate-sources`, triggering `exec-maven-plugin` to execute the two JARs sequentially.
3. **Generation**:
    - **Framework Code Phase**: `framework.jar` is invoked to output base Quarkus application framework code to the project directory.
    - **Business Code Phase**: `generator.jar` is invoked to read Tenant A's configurations, connect to Trino for table metadata, and use Handlebars templates to generate GraphQL Schema, Java entity classes, Resolver, and **Tenant A-specific `application.yaml`**.
4. **Compilation & Deployment**: Maven automatically compiles generated code, then proceeds with packaging, container image building, and deployment to Tenant A's specified K8s environment using Tenant A's credentials.

## 5. Security Authentication Design

### 5.1 Application Layer Security (Generated Code)
The generated code includes a JWT filter with the following logic:
1. **Extraction**: Extract JWT token from the HTTP request's Authorization header.
2. **Parsing**: Parse JWT payload, **only extracting the username field** (e.g., `preferred_username`), **without verifying the token signature**.
3. **Comparison**: Compare the username against the `allowed_users` list configured in `tenant.yaml`.
4. **Decision**: If username is in the allowed list, pass the request; otherwise return 401 Unauthorized.

### 5.2 Security Boundary with Trino
- **Separation of Duties**: Application layer performs only **initial identity screening** (whether user is allowed to access this service instance). **Data permission verification** (whether user can query certain tables/fields) is entirely handled by the downstream Trino engine through Ranger integration.
- **Credential Passing**: The current request's username is passed to Trino via connection pool configuration for permission verification at the Trino level.

## 6. Deployment Architecture Design

### 6.1 Fully Isolated Deployment Model
Each tenant's service instance is deployed in a **completely independent Kubernetes namespace** with:
- Independent network policies and Ingress (configured with dedicated domain)
- Independent ConfigMaps and Secrets for application configuration and Trino credentials
- Independent resource quotas and Pod replicasets

### 6.2 Kubernetes Resource Configuration Management
**Important Clarification**: Kubernetes resource configuration files (Deployment, Service, Ingress, etc.) are **NOT generated by the Generator JAR**. Instead, they are pre-existing template files in the sample repository's `k8s/` directory.

**Configuration Approach**:
- The sample repository contains Kubernetes manifest templates with placeholders (e.g., `{{tenant.id}}`, `{{tenant.domain}}`)
- During the CI/CD pipeline execution, these templates are processed with the tenant-specific configuration values
- This approach provides greater flexibility, allowing users to customize Kubernetes configurations as needed
- The Generator JAR only produces application-level configuration (`application.yaml`), not infrastructure-level K8s manifests

## 7. CI/CD and Operations

### 7.1 Independent Pipeline per Tenant
Each tenant project is associated with an independent CI/CD pipeline using that tenant's own K8s access credentials and image registry secrets, automating deployment to their dedicated environment.

### 7.2 Monitoring and Operations
- **Independent Observability**: Logs, metrics, and tracing data for each tenant instance are collected in isolation where possible
- **Independent Lifecycle Management**: Each tenant's service can be independently scaled, restarted, upgraded, and rolled back without affecting other tenants

## 8. Summary
This system achieves complete service isolation through the architecture of "**one tenant, one independent project, one generation, one independent environment**". The code generator transforms simple table field configurations and tenant deployment information into a production-ready Quarkus GraphQL service with basic security authentication. Data security responsibility remains clearly with the Trino+Ranger component, ensuring proper separation of concerns.
